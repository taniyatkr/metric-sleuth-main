# Metric Sleuth: GTM Metrics Explorer

## MCP-Powered GTM Metrics Exploration

This is Layer 1 of **metric-sleuth** — a workflow, not an agent. It answers
seven known, descriptive questions about Wavemark's go-to-market data by
following a fixed, predetermined path through the shared MCP server
(`../mcp_server/analytics_server.py`): every question below maps to one
straight-line sequence of hand-authored SQL queries, decided in code, not
by a model. That's deliberate — it's the counterpart to
[`gtm-intelligence-investigator`](../gtm-intelligence-investigator/README.md),
which handles the open-ended questions where the steps genuinely aren't
knowable in advance. This project is the proof that you don't reach for an
agent when you don't need one.

Every query in this layer is authored directly, not generated by a model
and not copied from the server's own purpose-built tools — it runs
through the server's generic `run_query` passthrough, the same way any
other read-only SQL would. Claude's role here was limited to wiring each
query through the MCP protocol correctly; the SQL itself, and every
decision about what it should compute, is the analyst's.

## The seven questions

1. What does our pipeline look like right now?
2. What's our win rate and average sales cycle — overall and by segment?
3. What was MRR last month, and what's the trend over the last N months?
4. What does the ARR waterfall look like for a given month?
5. What's our NRR and GRR — blended and by segment, for a given period?
6. Who are our top accounts by revenue this month?
7. What does our support ticket volume/category/priority mix look like?

## Running it

No API key needed for this layer — it's plain tool calls, no model.

```bash
cd gtm-metrics-explorer
python3 explorer.py                          # full business review, all 7 questions
python3 explorer.py pipeline                  # just Q1/Q2
python3 explorer.py retention 2025-09 2026-08 # just Q5, for a specific period
```

Question types and their arguments: `pipeline`, `win_rate` (no args),
`mrr_trend <start_month> <end_month>`, `arr_waterfall <month>`,
`retention <base_month> <current_month>`, `top_accounts <month>`,
`tickets <start_month> <end_month>`. Months use `YYYY-MM`.

## How it works

`explorer.py` opens a real MCP client session against
`analytics_server.py` (spawned as a subprocess over stdio — the genuine
protocol, the same one `tests/` exercises). Each of the seven report
functions builds one or more hand-authored SQL query strings — defined
at the top of the file, right above the report functions that use them —
and runs each one for real through the server's generic `run_query`
tool, then formats the result alongside the query that produced it. None
of the seven questions calls a purpose-built tool with its own baked-in
query; `run_query` is a plain passthrough, so the SQL that executes is
exactly the SQL printed in the output, not a display copy of it.

A couple of queries lean on CTEs rather than subqueries or Python-side
math: Q2's win rate breaks closed-won and closed-lost into their own
CTEs before combining them per segment, Q4's ARR waterfall buckets each
account's revenue movement into new/expansion/contraction/churned in one
pass instead of computing the buckets in Python from two separate
queries, and Q5's NRR/GRR caps each account's current revenue at its own
base revenue (SQLite's scalar `MIN(a, b)`) inside a CTE rather than after
the fact. Two things were tried and deliberately dropped: a by-stage
breakdown of open pipeline for Q1 (most early-stage deals have no
`qualified_amount` yet, and `stage` reflects a deal's *current* stage,
not what it was back when the deal was created — that only works with
point-in-time snapshot data, which this dataset doesn't have), and a
prior-period-snapshot basis for pipeline value more generally, for the
same reason — "pipeline value" here always means pipeline *created* in a
period (`created_date`), never a value "as of" a past date.

The `explore(question_type, **kwargs)` function at the bottom is a
lookup table, not a decision — it's the clearest illustration in this
repo of what "workflow" means versus "agent": the path, and the query,
are both fixed before the question is even asked.
